## 1. ภาพรวมระบบ

AUN-QA Copilot ช่วยหลักสูตรจัดทำรายงานประเมินตนเอง (SAR) ตามเกณฑ์ AUN-QA ซึ่งมี 53 ข้อ งานหนึ่ง "รอบ" ไหลจากหลักสูตรขึ้นไปหาคณะ แล้วไปหากรรมการภายนอก ดังนี้ ประธานหลักสูตรเปิดรอบและแบ่งข้อให้อาจารย์เขียน อาจารย์เขียนแล้วกด "ส่งตรวจ" ประธานอนุมัติทีละข้อ เมื่ออนุมัติครบ 53 ข้อ ประธานส่งทั้งรอบให้ QA คณะ QA คณะอนุมัติแล้วส่งต่อคณบดี คณบดีอนุมัติสุดท้ายและล็อกเอกสาร จากนั้นผู้ดูแลมหาวิทยาลัยหรือ QA คณะมอบหมายกรรมการ กรรมการให้คะแนนแล้วส่งผล ประธานนำข้อเสนอแนะไปทำแผนปรับปรุง แล้วปิดรอบ ทุกจุดที่งานเปลี่ยนมือ ระบบส่งแจ้งเตือนเข้า "กระดิ่ง" มุมขวาบนของผู้รับ

### แผนภาพการส่งต่องาน

ระดับข้อ (ทำซ้ำทีละข้อ จนครบ 53 ข้อ):

**ประธาน** มอบหมายข้อ → **อาจารย์** เขียน + ส่งตรวจ → **ประธาน** อนุมัติ (หรือส่งกลับ → อาจารย์แก้ → ส่งตรวจใหม่)

ระดับรอบ:

**ประธาน** ส่งรอบ → **QA คณะ** อนุมัติ → **คณบดี** อนุมัติสุดท้ายและล็อก → **ผู้ดูแลมหาวิทยาลัย / QA คณะ** มอบหมายกรรมการ + เริ่มประเมิน → **กรรมการ** ให้คะแนน + เสร็จสิ้นการประเมิน → **ประธาน** ทำแผนปรับปรุง → **ผู้ดูแลมหาวิทยาลัย / ประธาน / QA คณะ** ปิดรอบ

| ขั้น | ผู้ทำ | กดอะไร | งานไปหาใคร (ได้แจ้งเตือน) |
|---|---|---|---|
| 1 | ประธานหลักสูตร | สร้างรอบ → มอบหมายข้อ → เริ่มดำเนินการ | อาจารย์ที่ได้รับมอบหมาย |
| 2 | อาจารย์ (เจ้าของข้อ) | เขียน → "ส่งตรวจ" | ประธานหลักสูตร (ยกเว้นตัวผู้ส่งเอง) |
| 3 | ประธานหลักสูตร | "อนุมัติข้อนี้" หรือ "ส่งกลับแก้ไข" | เจ้าของข้อ |
| 4 | ประธานหลักสูตร | อนุมัติครบ 53 ข้อ → "ส่งให้ QA คณะตรวจ" | QA คณะ |
| 5 | QA คณะ | "อนุมัติ (QA คณะ)" หรือ "ส่งกลับแก้ไข" | คณบดี (หรือกลับไปหาประธาน) |
| 6 | คณบดี | "อนุมัติสุดท้ายและล็อก" หรือ "ส่งกลับแก้ไข" | ผู้ดูแลมหาวิทยาลัย + QA คณะ (หรือกลับไปหาประธาน) |
| 7 | ผู้ดูแลมหาวิทยาลัย / QA คณะ | "มอบหมายกรรมการ" → "เริ่มการประเมิน" | กรรมการ |
| 8 | กรรมการ | ให้คะแนน 8 เกณฑ์ + verdict → "เสร็จสิ้นการประเมิน" | ประธาน, QA คณะ, ผู้ดูแลมหาวิทยาลัย |
| 9 | ประธานหลักสูตร | สร้างแผนปรับปรุงจากข้อเสนอแนะ (AFI) | ผู้รับผิดชอบแผน |
| 10 | ผู้ดูแลมหาวิทยาลัย / ประธาน / QA คณะ | "ปิดรอบ" | (ไม่มีแจ้งเตือน) |

ข้อสำคัญที่ต้องจำ: **ผู้อนุมัติรายข้อมีแค่ประธานหลักสูตร** และ **ใครเป็นผู้เขียนเนื้อหาล่าสุดของข้อไหน จะอนุมัติข้อนั้นเองไม่ได้** (หลักแยกหน้าที่) ดังนั้นหลักสูตรที่มีประธานคนเดียว ประธานไม่ควรเขียนข้อที่ตัวเองต้องอนุมัติ

หมายเหตุ
- QA คณะและคณบดี "ส่งกลับ" รายข้อได้ แต่ **อนุมัติรายข้อไม่ได้** (สิทธิ์ `sar.approve` มีแค่ประธาน — `eduflow-next/lib/api/rbac.ts`)
- หลักสูตร DS (`lect2`) **ไม่มีประธาน** ในข้อมูลเดโม่ ถ้าสร้างรอบให้ DS จะไม่มีใครมอบหมาย/อนุมัติได้
- เมนูอ้างจาก `eduflow-next/components/aunqa/AppSidebar.tsx` บัญชีอ้างจาก `eduflow-next/lib/mock-data/aunqa/org.ts`

## 3. ลำดับขั้นทั้งกระบวนการ: ใครกดอะไร

### 3.1 สถานะของข้อ (53 ข้อต่อรอบ)

ยังไม่เริ่ม → กำลังเขียน → รอตรวจ → อนุมัติแล้ว (หรือ ส่งกลับแก้ไข → กำลังเขียน → รอตรวจ อีกรอบ)

| จาก → ไป | ใครกด | ปุ่ม | เงื่อนไข | ใครได้แจ้งเตือน |
|---|---|---|---|---|
| ยังไม่เริ่ม → กำลังเขียน | เจ้าของข้อ / ประธาน | (อัตโนมัติเมื่อบันทึกเนื้อหาครั้งแรก) | — | ไม่มี |
| กำลังเขียน → รอตรวจ | เจ้าของข้อ / ประธาน | "ส่งตรวจ" | ต้องมีเนื้อหา · รอบต้องยังแก้ได้ | ประธานหลักสูตร **ยกเว้นตัวผู้ส่ง** |
| รอตรวจ → อนุมัติแล้ว | ประธานเท่านั้น | "อนุมัติข้อนี้" (หรือในคิว "รอตรวจ") | ประธานต้องไม่ใช่ผู้เขียนเนื้อหาล่าสุด | เจ้าของข้อ |
| รอตรวจ → ส่งกลับแก้ไข | ประธาน / QA คณะ / คณบดี | "ส่งกลับแก้ไข" | ต้องใส่เหตุผล | เจ้าของข้อ |
| อนุมัติแล้ว → ส่งกลับแก้ไข | ประธาน / QA คณะ / คณบดี | "ส่งกลับแก้ไข" | ต้องใส่เหตุผล | เจ้าของข้อ |
| ส่งกลับแก้ไข → รอตรวจ | เจ้าของข้อ / ประธาน | แก้แล้ว "ส่งตรวจ" | — | ประธาน (ยกเว้นผู้ส่ง) |

ข้อที่ "รอตรวจ" แล้ว **แก้ไม่ได้และส่งซ้ำไม่ได้** จนกว่าจะถูกส่งกลับ (`eduflow-next/lib/api/workflow.ts` `SECTION_TRANSITIONS`)

### 3.2 สถานะของรอบ

ร่าง → กำลังดำเนินการ → รอ QA คณะ → QA คณะอนุมัติ → อนุมัติสุดท้าย (ล็อก) → กำลังประเมิน → ประเมินแล้ว → ปิดรอบ (มีทางแยก "ส่งกลับแก้ไข" จาก QA คณะ/คณบดี และ "เปิด revision ใหม่" หลังล็อก)

| จาก → ไป | ใครกด | ปุ่ม (หน้า `/app/cycles/{รอบ}`) | เงื่อนไข | ใครได้แจ้งเตือน |
|---|---|---|---|---|
| (สร้าง) → ร่าง | ประธาน / ผู้ดูแลมหาวิทยาลัย | ฟอร์มที่ `/app/cycles` | ปีซ้ำไม่ได้ ระบบสร้าง 53 ข้อให้ | ไม่มี |
| ร่าง → กำลังดำเนินการ | ประธาน / ผู้ดูแลมหาวิทยาลัย | "เริ่ม/กลับไปดำเนินการ" | — | เจ้าของข้อทุกคน + ประธาน |
| กำลังดำเนินการ → รอ QA คณะ | ประธาน | "ส่งให้ QA คณะตรวจ" | **อนุมัติครบ 53 ข้อ** | QA คณะ + เจ้าของข้อ |
| รอ QA คณะ → QA คณะอนุมัติ | QA คณะ | "อนุมัติ (QA คณะ)" | — | คณบดี + เจ้าของข้อ + ประธาน |
| รอ QA คณะ → ส่งกลับแก้ไข | QA คณะ | "ส่งกลับแก้ไข" | ต้องใส่เหตุผล | เจ้าของข้อ + ประธาน |
| QA คณะอนุมัติ → อนุมัติสุดท้าย | คณบดี | "อนุมัติสุดท้ายและล็อก" | ล็อก + บันทึก hash | ผู้ดูแลมหาวิทยาลัย + QA คณะ + เจ้าของข้อ + ประธาน |
| QA คณะอนุมัติ → ส่งกลับแก้ไข | คณบดี | "ส่งกลับแก้ไข" | ต้องใส่เหตุผล | เจ้าของข้อ + ประธาน |
| ส่งกลับแก้ไข → กำลังดำเนินการ | ประธาน | "เริ่ม/กลับไปดำเนินการ" | — | เจ้าของข้อ + ประธาน |
| อนุมัติสุดท้าย → กำลังดำเนินการ (revision +1) | คณบดี | "เปิด revision ใหม่" | ต้องใส่เหตุผล ปลดล็อก | **ไม่มี** |
| อนุมัติสุดท้าย → กำลังประเมิน | ผู้ดูแลมหาวิทยาลัย / QA คณะ | "เริ่มการประเมิน" | มอบหมายกรรมการก่อน | กรรมการ + เจ้าของข้อ + ประธาน |
| กำลังประเมิน → ประเมินแล้ว | กรรมการ | "เสร็จสิ้นการประเมิน" | กรรมการ **ทุกคน** ให้คะแนนครบทุกเกณฑ์ + มี verdict | ประธาน + QA คณะ + ผู้ดูแลมหาวิทยาลัย |
| ประเมินแล้ว → ปิดรอบ | ประธาน / ผู้ดูแลมหาวิทยาลัย / QA คณะ | "ปิดรอบ" | — | **ไม่มี** |

### 3.3 การรับผู้ใช้ใหม่

1. **ขอเข้าใช้งานเอง** ที่ `/request-access` (อีเมลต้องเป็นโดเมนของมหาวิทยาลัย เช่น `@sample-uni.example`) → ผู้ดูแลได้แจ้งเตือน → ผู้ดูแลเปิด `/app/admin?tab=requests` แล้ว **อนุมัติ** (เลือกบทบาท + ขอบเขต ผู้ขอได้แจ้งเตือน "บัญชีของคุณได้รับอนุมัติแล้ว") หรือ **ปฏิเสธ** (ข้อมูลถูกลบทันที ผู้ขอไม่ได้รับแจ้ง)
2. **เชิญ** ผู้ดูแลกด "เชิญ" ที่แท็บผู้ใช้ → ระบบแสดงลิงก์ `/invite#t=…` ให้คัดลอกไปส่งเอง (ระบบไม่ส่งอีเมล) → ผู้ถูกเชิญเปิดลิงก์ ตั้งรหัสผ่าน แล้วเข้าระบบได้ทันที ผู้เชิญได้แจ้งเตือน
3. **สร้างบัญชีตรง** ผู้ดูแลกรอกฟอร์มเพิ่มผู้ใช้ บัญชีใช้งานได้ทันที
4. **ระงับ / เปิดใช้** บัญชีที่ถูกระงับเข้าระบบไม่ได้ และไม่ได้รับแจ้งเตือนใด ๆ · ลบได้เฉพาะบัญชีที่ยังรอเชิญหรือรออนุมัติ

## 5. กรณีที่เจ้าของเจอ: ประธานไม่ได้รับแจ้งเตือนหลัง "บันทึก" + "ส่งตรวจ"

### สรุปสั้น

ระบบส่งแจ้งเตือนถูกต้องตามกติกา แต่ **ข้อมูลเดโม่เดิมบังคับให้ต้องใช้บัญชีประธานเขียนและส่งเอง** และ **ข้อความบนจอเดิมบอกผิดว่าประธานได้รับแจ้งเตือนแล้ว** จึงดูเหมือนระบบพัง

### สาเหตุ (ภาษาคน)

1. **ประธานส่งเอง ไม่แจ้งตัวเอง** — แจ้งเตือน "ส่งตรวจ" ส่งถึงประธานทุกคนของหลักสูตร *ยกเว้นคนที่กด* หลักสูตร CS มีประธานคนเดียวคือ `chair1` ถ้า `chair1` เป็นคนกด ผู้รับจึงเหลือ 0 คน
2. **"บันทึก" อย่างเดียวไม่แจ้งใคร** — แจ้งเตือนเกิดตอนกด "ส่งตรวจ" แล้วยืนยันเท่านั้น
3. **ข้อมูลเดโม่เดิมไม่มีข้อที่อาจารย์ส่งได้** — ข้อที่ยังเขียนได้มี 3.6, 5.1, 7.9 และทั้งสามข้อไม่มีเจ้าของ อาจารย์ (`staff1`) จึงแก้ไม่ได้ คนเดียวที่แก้ได้คือประธาน → วนกลับไปข้อ 1
4. **ข้อมูลอยู่ในเบราว์เซอร์** — ระบบเดโม่เก็บข้อมูลใน `localStorage` ของเบราว์เซอร์ ถ้าเปิดอาจารย์ใน Chrome แล้วเปิดประธานใน Edge หรือหน้าต่างไม่ระบุตัวตน สองฝั่งจะเห็นข้อมูลคนละชุด แจ้งเตือนจึงไม่ข้ามไปหากัน
5. **ปุ่มระดับรอบแจ้ง QA คณะ ไม่ใช่ประธาน** — ปุ่ม "ส่งให้ QA คณะตรวจ" บนหน้ารอบเป็นการส่งทั้งรอบไปหา QA คณะ และกดได้ก็ต่อเมื่ออนุมัติครบ 53 ข้อ (ข้อมูลเดโม่ยังขาด 8 ข้อ)
6. ผลข้างเคียง: ประธานที่เป็นผู้เขียนล่าสุด **อนุมัติข้อนั้นเองไม่ได้** และไม่มีบทบาทอื่นอนุมัติรายข้อได้ ข้อจึงค้างที่ "รอตรวจ" จนกว่าจะส่งกลับแก้ไขแล้วให้คนอื่นเขียน

### ขั้นตอนที่ถูก (ลองซ้ำได้)

ใช้ **เบราว์เซอร์เดียวกัน แท็บเดียวกัน** ตลอด และออกจากระบบก่อนสลับบัญชีทุกครั้ง

1. เข้า `sadmin` → เมนู ผู้ดูแลระบบ → แท็บ "ข้อมูลเดโม่" (`/app/admin?tab=demo`) → กด "รีเซ็ตเป็นข้อมูลมาตรฐาน" → ยืนยัน (ระบบพาไปหน้าเข้าสู่ระบบ) — ทำครั้งแรกครั้งเดียว เพื่อให้ได้ข้อมูลเดโม่ชุดใหม่ (เบราว์เซอร์ที่เคยเปิดเดโม่มาก่อนยังเป็นข้อมูลชุดเก่า)
2. เข้า `chair1` → ดูกระดิ่ง ต้องมีแจ้งเตือนยังไม่อ่าน 5 รายการ ("ข้อ 1.5 ส่งตรวจแล้ว รอประธานอนุมัติ" ฯลฯ) → ออกจากระบบ

4. กล่องยืนยันต้องขึ้น "ประธานหลักสูตร 1 คนจะได้รับแจ้งเตือน" → กด "ยืนยันส่งตรวจ" → ข้อความ "ส่งตรวจข้อ 3.6 แล้ว — แจ้งประธานหลักสูตร 1 คน" → ออกจากระบบ
5. เข้า `chair1` → กระดิ่ง +1 "ข้อ 3.6 ส่งตรวจแล้ว รอประธานอนุมัติ" → กดรายการ → ไปหน้าข้อ 3.6 → "อนุมัติข้อนี้" (หรือ "ส่งกลับแก้ไข" พร้อมเหตุผล)
6. เข้า `staff1` อีกครั้ง → กระดิ่งมี "ข้อ 3.6 ได้รับการอนุมัติแล้ว" (หรือ "ข้อ 3.6 ถูกส่งกลับแก้: …")

ถ้าอยากลองข้อ 5.1 หรือ 7.9 ให้ `chair1` มอบหมายข้อนั้นให้ `staff1` ก่อนที่ `/app/cycles/cycle-demo-2569/assign` แล้วเดินขั้น 3–6

ถ้าอยากเห็นกรณี "ประธานส่งเอง": เข้า `chair1` เปิดข้อ 5.1 → เขียน → "ส่งตรวจ" → กล่องยืนยันจะเตือน "ส่งแล้วจะไม่มีใครได้รับแจ้งเตือน" (ระบบยอมให้ส่ง แต่บอกล่วงหน้าแล้ว)

## 8. คำถามพบบ่อย / ข้อควรระวังเวลาลองเล่น

**ใช้หลายเบราว์เซอร์พร้อมกันได้ไหม?** ไม่ได้ ข้อมูลเดโม่อยู่ในเบราว์เซอร์ที่เปิดอยู่เท่านั้น ใช้เบราว์เซอร์เดียวและออกจากระบบก่อนสลับบัญชี ถ้าเปิดหลายแท็บพร้อมกัน แท็บอื่นจะถูกพาไปหน้าเข้าสู่ระบบเมื่อมีการสลับบัญชี

**ทำไมข้อมูลไม่เหมือนในเอกสารนี้?** เบราว์เซอร์ที่เคยเปิดเดโม่ก่อน TASK-0003 ยังเป็นข้อมูลชุดเก่า ให้ `sadmin` กด "รีเซ็ตเป็นข้อมูลมาตรฐาน" หนึ่งครั้ง

**กดบันทึกแล้วทำไมประธานไม่รู้?** "บันทึก" เก็บงานเฉย ๆ ต้องกด "ส่งตรวจ" แล้วยืนยันก่อน ประธานจึงได้แจ้งเตือน

**ประธานกดอนุมัติไม่ได้ ขึ้น "คุณเขียนเอง"** ประธานเป็นผู้เขียนเนื้อหาล่าสุดของข้อนั้น ให้กด "ส่งกลับแก้ไข" ก่อน แล้วมอบหมายให้อาจารย์ปรับและส่งตรวจใหม่ ถ้าอาจารย์ส่งโดยไม่แก้เนื้อหาเลย ผู้เขียนล่าสุดยังเป็นประธานอยู่ (กล่องยืนยันจะเตือน) ต้องแก้หรือเพิ่มเนื้อหาก่อนส่ง

**ส่งตรวจไปแล้ว อยากแก้ต่อ** ข้อที่รอตรวจแก้ไม่ได้ ต้องให้ประธาน (หรือ QA คณะ/คณบดี) ส่งกลับก่อน

**ปุ่ม "ส่งให้ QA คณะตรวจ" กดไม่ได้** ต้องอนุมัติครบ 53 ข้อ ข้อมูลเดโม่มาตรฐานอนุมัติแล้ว 45 ข้อ ยังขาด 8 ข้อ

**อาจารย์เปิดข้อแล้วแก้ไม่ได้** อาจารย์แก้ได้เฉพาะข้อที่ตัวเองเป็นเจ้าของ และข้อนั้นต้องอยู่สถานะ "ยังไม่เริ่ม / กำลังเขียน / ส่งกลับแก้ไข" ให้ประธานมอบหมายก่อน

**ล็อกอินแล้วขึ้น "รออนุมัติ"** บัญชีนั้นส่งคำขอแล้วแต่ผู้ดูแลยังไม่อนุมัติ ให้เข้า `uadmin` → `/app/admin?tab=requests`

**ลิงก์เชิญหายไป** หน้าเข้าสู่ระบบแสดงลิงก์เชิญจากการโหลดชุดข้อมูลครั้งเดียว (รีเฟรชแล้วหาย และกล่องสรุปหายเองหลัง 10 นาที) ถ้าหายให้โหลดเคส `user-invited` ใหม่ หรือให้ `uadmin` ออกลิงก์ใหม่

**กระดิ่งไม่ขึ้นทันที** กดไปหน้าอื่นหรือรีเฟรชหนึ่งครั้ง ระบบนับใหม่ตอนเปลี่ยนหน้า

**ข้อควรระวัง:** โหลดชุดข้อมูลทดสอบหรือรีเซ็ต = ข้อมูลทุกอย่างที่ลองไว้หายหมด ย้อนกลับไม่ได้
