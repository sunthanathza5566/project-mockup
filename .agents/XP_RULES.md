# XP RULES — กติกาการเติบโต

## หลักคิด
XP วัดจาก **ผลงานที่ผ่านด่านจริง** ไม่ใช่ปริมาณงาน ผู้ให้ XP คือ xp-keeper เท่านั้น
โดยดูหลักฐานใน TASK file, review report และผลเทสต์

## ตารางคะแนน
| เหตุการณ์ | XP |
|-----------|----|
| ส่งงานเฟสตัวเองเสร็จ ขนาด S / M / L | +10 / +20 / +40 |
| ผ่าน review รอบแรก ไม่ต้องแก้ | +10 |
| ต้องแก้หลัง review (ต่อรอบ) | -3 |
| เทสต์ที่ตัวเองเขียน/งานตัวเองผ่านเทสต์ครบครั้งแรก | +5 |
| reviewer / qa / security / ui-inspector / playtester เจอปัญหาจริงระดับ major ขึ้นไป (ผู้ที่เจอ) | +8 ต่อปัญหา |
| finding ที่ถูกตีกลับว่าไม่ใช่ปัญหาจริง (false positive) | -2 |
| diagram-designer: diagram ตรงกับโค้ดจริงเมื่อ reviewer/code-reader สุ่มตรวจ | +5 |
| thesis-writer: export เล่มสำเร็จ และ `build.py check` ไม่มี diagram หาย | +5 |
| thesis-writer: เขียนข้อมูล/ตัวเลข/อ้างอิงที่ไม่มีหลักฐานลงเล่ม | -30 (ถือเป็นละเมิด PROTOCOL) |
| บทเรียนของตัวเองถูกรับเข้า playbook | +3 |
| บทเรียนใน playbook ถูกอ้างว่าช่วยป้องกันปัญหาในงานอื่น (ผู้เขียนบทเรียน) | +5 |
| BLOCKED อย่างถูกต้อง (ถามแทนเดา แล้วคำถามนั้นสำคัญจริง) | +5 |
| bug ที่หลุดไปถึง staging/production ย้อนกลับมาที่งานตัวเอง | -15 |
| งานถูก revert | -20 |
| ละเมิด OWNERSHIP หรือ PROTOCOL ข้อห้าม | -30 และบันทึกเหตุใน playbook |

XP ต่ำสุดคือ 0 (ไม่ติดลบ) แต่บันทึกลบยังอยู่ใน ledger

## Level
| Level | XP สะสม | ชื่อ | สิทธิ์ที่ได้เพิ่ม |
|-------|---------|------|------------------|
| 1 | 0 | Rookie | ทำงานตามแผน architect เท่านั้น ทุกงานต้อง review |
| 2 | 60 | Member | งาน S ในโซนตัวเอง เสนอวิธีทำเองได้ (ไม่ต้องรอแผน) แต่ยังต้อง review |
| 3 | 180 | Senior | เสนอเพิ่มบทเรียนเป็น **RULE** (กฎบังคับ) ได้, review งาน S ของ Level 1-2 ในโซนเดียวกันได้ (ไม่แทน reviewer ในงาน M/L) |
| 4 | 400 | Lead | แตก subtask ในโซนตัวเองเองได้, เป็นพี่เลี้ยง: playbook ส่วน RULE ถูกแนบให้ agent โซนใกล้เคียงอ่าน |
| 5 | 800 | Master | เสนอแก้ PROTOCOL/OWNERSHIP ได้ (เจ้าของโปรเจกต์อนุมัติ) |

**ทุก level ไม่ได้รับสิทธิ์ข้าม:** การอนุมัติของเจ้าของสำหรับ deploy / migration / ลบข้อมูล / production, security audit, และกฎห้ามใน PROTOCOL

## Playbook (ความรู้ที่โตขึ้นจริง)
ไฟล์: `.agents/memory/<agent>/playbook.md` มี 3 ส่วน
- **RULES** — กฎที่พิสูจน์แล้ว (ใช้ได้ซ้ำ ≥ 2 งาน หรือมาจาก incident) ต้องทำตามเสมอ
- **LESSONS** — บทเรียนใหม่ ยังไม่พิสูจน์ซ้ำ
- **PROJECT KNOWLEDGE** — ข้อเท็จจริงเฉพาะโปรเจกต์ที่ต้องรู้ (path สำคัญ, gotcha, convention)

เกณฑ์รับบทเรียน: เฉพาะเจาะจง, ทำซ้ำได้, ตรวจสอบได้, ไม่ซ้ำของเดิม
ตัวอย่างดี: "ทุก endpoint ใหม่ใน `src/api/` ต้องผ่าน middleware `requireRole()` — เคยหลุดใน TASK-0007"
ตัวอย่างไม่ดี: "เขียนโค้ดให้ดี"

ขนาด: playbook ละไม่เกิน ~120 บรรทัด เกินแล้ว xp-keeper รวม/ตัดบทเรียนที่ล้าสมัย
บทเรียนใน LESSONS ที่ถูกใช้ซ้ำได้ผล 2 ครั้ง → เลื่อนเป็น RULES
