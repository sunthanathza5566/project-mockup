### 1) การรับผู้ใช้ใหม่แบบ role-based
**หลักการที่ยืนยันแล้ว**
- ระบบองค์กรมักสร้างบัญชีด้วยมือ ส่วนการสมัครเองเป็น "อัตโนมัติหรือกึ่งอัตโนมัติ" และต้องตรวจว่า "ลงทะเบียนเป็น role ต่าง ๆ ได้หรือไม่" และ "มีคนตรวจก่อนให้สิทธิ์หรือไม่" (OWASP WSTG-IDNT-02, R1)
- ห้ามให้ client กำหนดฟิลด์สิทธิ์: ตัวอย่างคลาสสิกคือเติม `isAdmin=true` ตอนสมัครแล้วได้ admin → ใช้ allowlist/DTO ที่ไม่มีฟิลด์สิทธิ์ (OWASP Mass Assignment, R2) ⇒ **ฟอร์มสมัครเองต้องไม่มีช่องเลือก role**
- Least privilege + deny by default + ตรวจสิทธิ์ทุก request + ระวัง privilege creep และ "ให้เพิ่มทีหลังง่ายกว่าดึงคืน" (OWASP Authorization, R3) ⇒ ผู้สมัคร/ผู้ถูกเชิญที่ยังไม่อนุมัติ = 0 สิทธิ์
- Separation of duty = "ไม่มีผู้ใช้คนใดมีสิทธิ์พอจะใช้ระบบผิดได้คนเดียว" ทำได้แบบ static (role ที่ห้ามถือพร้อมกัน) หรือ dynamic (two-person rule) (NIST CSRC glossary อ้าง SP 800-192, R4) ⇒ คนขอ ≠ คนอนุมัติ; ผู้อนุมัติห้ามอนุมัติคำขอของตัวเอง
- โทเคนในลิงก์ (ใช้ได้กับลิงก์เชิญ): สุ่มด้วย CSPRNG, ยาวพอกัน brute force, ใช้ครั้งเดียว, หมดอายุ, เก็บแบบปลอดภัย, ตอบข้อความเหมือนกันไม่ว่าบัญชีมีหรือไม่ (OWASP Forgot Password, R5)
- รหัสผ่าน: ใช้รหัสผ่านเป็นปัจจัยเดียว ขั้นต่ำ **15** ตัว (ถ้าเป็นส่วนของ MFA ขั้นต่ำ 8), ยอมรับยาว ≥64, **ห้ามบังคับผสมชนิดอักขระ**, ต้องเทียบ blocklist (NIST SP 800-63B-4 §3.1.1.2, R6)
- Moodle (LMS มหาวิทยาลัย): มีทั้ง "Manual accounts — admin สร้าง" และ "Email-based self-registration"; เอกสารเตือนว่าเปิดสมัครเองทำให้ spammer สร้างบัญชีได้ แนะนำจำกัด **allowed email domains** หรือเปิดช่วงสั้น ๆ แล้วปิด (R7, R8)
- Supabase (ถ้าวันหน้าย้ายขึ้น backend จริง): `auth.admin.inviteUserByEmail(email, {data, redirectTo})` ส่งลิงก์เชิญ ต้องเรียกฝั่ง server ด้วย service-role key เท่านั้น (R9)
- PDPA: เก็บเท่าที่จำเป็นต่อวัตถุประสงค์ (ม.22) และต้องแจ้งรายละเอียด/Privacy Notice (ม.23), ใช้ตามวัตถุประสงค์ที่แจ้ง (ม.21) — **แหล่งรอง** (R10, ไม่ได้เปิดตัวบทราชกิจจาฯ)

**ตารางเทียบ 4 แบบ**
| แบบ | ข้อดี | ข้อเสีย / ความเสี่ยง | ทำได้ใน MVP localStorage? |
|---|---|---|---|
| A. Admin สร้างบัญชี + ตั้งรหัสชั่วคราว (มีแล้ว) | ควบคุมเต็ม, role กำหนดโดย admin, ไม่มีคิว | admin รู้รหัสผ่านผู้ใช้ (ต้องบังคับเปลี่ยนครั้งแรก), ภาระ admin, ส่งรหัสนอกระบบ | ได้ (มีอยู่) |
| B. เชิญ: admin กำหนด role+ขอบเขต → ได้ลิงก์/รหัสเชิญ → ผู้ใช้ตั้งรหัสเอง | admin ไม่รู้รหัสผ่าน, role ถูกล็อกในคำเชิญ (กัน mass assignment), audit ชัด, เป็นแบบมาตรฐาน SaaS/Supabase | ต้องมีช่องทางส่งลิงก์ (อีเมล), โทเคนรั่ว = คนอื่นรับสิทธิ์ → ต้อง single-use + หมดอายุ | **ได้แบบจำลอง**: ไม่มีอีเมล → แสดงลิงก์/รหัสให้ admin คัดลอกไปส่งเอง (LINE/อีเมลองค์กร) |
| C. สมัครเอง + รออนุมัติ | ผู้ใช้เริ่มเองได้, ลดงาน admin ตอนกรอกข้อมูล | spam/ปลอมตัว (R8), ต้องมีคิว+SLA อนุมัติ, เก็บข้อมูลคนที่ไม่ได้รับอนุมัติ (PDPA ต้องกำหนดระยะลบ), เสี่ยงให้ผู้สมัครเลือก role | ได้แบบจำลอง (คิวใน localStorage) แต่ "ยืนยันอีเมล" จำลองไม่ได้จริง |
| D. SSO / จำกัดโดเมนอีเมลมหาวิทยาลัย | ไม่ต้องจำรหัสใหม่, ปิดบัญชีตามระบบกลางเมื่อลาออก, ยืนยันตัวตนจริง | ต้องมี IdP (Google Workspace/Azure AD/ThaiREN), เชื่อมทำใน backend จริง; โดเมนอย่างเดียวไม่ได้บอก role | **ไม่ได้** (ไม่มี IdP/อีเมลจริง) — ใส่เป็นงานอนาคตในเล่ม |

### 2) Notification panel
**ยืนยันแล้ว**
- Badge ที่หัวหน้า (masthead) จำเป็นเมื่อมี drawer; กด badge = เปิด/ปิด panel; แสดงจำนวนและสถานะ unread (PatternFly, R11)
- เรียง **ใหม่→เก่า**; เวลาแบบสัมพัทธ์สำหรับรายการใหม่ (<1 ชม.) และเวลาจริงเมื่อเก่ากว่า; **unread = ตัวหนา**; เมนู "Mark all read"; กดรายการ = mark read; "Clear" ไม่ลบจากระบบ; ถ้าจัดกลุ่ม ไม่เกิน 3–4 กลุ่ม; ซ่อน badge ของกลุ่มเมื่อไม่มี unread (R11)
- **ห้ามใช้ panel เป็นที่เดียวสำหรับเรื่องที่ต้องทำทันที** — ใช้ modal/toast ประกอบ (R11) และ NN/g: notification แบบ passive "พลาดง่าย" จึงไม่เหมาะกับข้อมูลที่จำเป็น; notification ต้องให้บริบทพอเพราะมักมาตอนผู้ใช้ทำอย่างอื่น; badge หายเมื่อผู้ใช้ดูแล้ว (NN/g Flaherty 2024, R12)
- ไม่ควรโชว์ unread บน badge ถ้า unread มีค้างเกือบตลอด (จะไม่มีผล/รบกวน) (PatternFly notification badge — ผ่านผลค้นหา, R13 แหล่งรอง)
- Trigger เป็นปุ่มที่ควบคุมการแสดง: `role=button` + `aria-expanded` true/false + `aria-controls` (WAI-ARIA APG Disclosure, R14); การเปลี่ยนจำนวนต้องประกาศให้ screen reader โดยไม่ย้าย focus (WCAG 4.1.3 Status Messages — ตัวอย่างตะกร้า "5 items", R15) ⇒ label ของกระดิ่ง = "การแจ้งเตือน ยังไม่อ่าน 3 รายการ"
- โค้ดเรามีข้อมูลพอ: `readAt` (unread/read), `createdAt` (จัดกลุ่ม/เวลา), `cycleId`+`requirementId`+`kind` (deep link) — `lib/types.ts:172-176`

**อนุมาน (ไม่มีแหล่งมาตรฐานยืนยันตรง)**
- จัดกลุ่มตามวัน "วันนี้ / เมื่อวาน / ก่อนหน้า" (≤3 กลุ่มตามเพดาน R11) — เป็นแนวที่พบทั่วไปแต่ไม่พบในเอกสาร design system ที่เปิดได้
- Deep link ตาม kind: `assigned/changes_requested/comment/approved` → `/app/sections/<id>` (ข้อ SAR) · `cycle_status/deadline` → `/app/cycles/<cycleId>`; ถ้าเป้าหมายถูกลบ/ไม่มีสิทธิ์ → ไปหน้า cycle + toast "รายการนี้ไม่มีแล้ว"
- กดรายการ: mark read **แล้ว** นำทาง และปิด panel; ปุ่ม "อ่านทั้งหมด" เป็นข้อความ (ไม่ใช่ไอคอนเดี่ยว); ท้าย panel มีลิงก์ "ดูทั้งหมด" ถ้ารายการ >20
- Empty state: ไอคอน + "ยังไม่มีการแจ้งเตือน" + ประโยคอธิบายว่าจะเห็นอะไรที่นี่ (สอดคล้อง NN/g empty state ใน `standards/ui-ux.md` 5.2)
- Desktop (≥1024): popover กว้าง ~360–400px ใต้กระดิ่ง, สูงไม่เกิน ~70vh เลื่อนในตัว; Mobile (<640): sheet เต็มจอ/เต็มความกว้าง มีหัว + ปุ่มปิดข้อความ "ปิด"; Esc ปิดแล้วคืน focus ให้กระดิ่ง (สอดคล้อง AC-06 drawer)
- ไม่ควรมีทั้งกล่อง "แจ้งเตือน" ในหน้าหลักและ panel ซ้ำกัน — ภาพ v0 แสดงกล่อง "แจ้งเตือน (0 ใหม่)" กินพื้นที่ครึ่งจอใต้ "สิ่งที่ต้องทำ" → ย้ายไป panel แล้วหน้าหลักเหลือ "สิ่งที่ต้องทำ" (E2E อ้าง `noti-list` — ต้องย้าย testid ตาม)

### 3) Palette earth tone + warm dim (ทุกค่า **[คำนวณ]** ด้วยสูตร relative luminance WCAG 2.x — สคริปต์ Python ใน scratchpad ของ session นี้)
**หลักฐานด้านเหตุผล**
- Material Components: dark theme ใช้ "**dark grey แทน black** — เห็นเงาได้ และลดความล้าตาเมื่ออ่านตัวอักษรสว่าง"; พื้นยกระดับสว่างขึ้นตามระดับ (R16) [ยืนยัน] · ค่า `#121212` เป็นที่อ้างกันทั่วไปว่ามาจาก Material แต่หน้าสเปกเปิดไม่ได้ → [แหล่งรอง]
- Halation (ตัวอักษรสว่างฟุ้งบนพื้นดำ กระทบคนสายตาเอียง) — พบเฉพาะในบล็อก/ระบบออกแบบรอง (Trimble Modus ผ่านผลค้นหา) **[แหล่งรอง ไม่ใช้อ้างในเล่มเป็นข้อเท็จจริง]**
- งานวิจัย: Piepenbrock, Mayr, Mund & Buchner (2013) "Positive display polarity is advantageous for both younger and older adults" *Ergonomics* 56(7) 1116–1124 (ตรวจ bibliographic ด้วย Crossref, R17) — สนับสนุน **ค่าเริ่มต้นเป็นโหมดสว่าง** (ตรงกับที่เจ้าของสั่ง) [ยืนยันชื่อ/ผลตามชื่อเรื่อง; ไม่ได้อ่านเนื้อหาเต็ม]
- เกณฑ์: ข้อความ ≥4.5, UI/ขอบ/ไอคอน ≥3 (ตาม `standards/ui-ux.md` 3)

### 4) UI สำหรับผู้ใช้ไม่ถนัดเทคโนโลยี
**ยืนยันแล้ว**
- ไอคอนต้องมี **ข้อความกำกับเสมอ แสดงตลอด ไม่ใช่แค่ hover** (hover เพิ่ม interaction cost และใช้บนจอสัมผัสไม่ได้); ไอคอนที่คนรู้จักแทบสากลมีน้อย (home, print, search) (NN/g Harley 2014, R18) · utility ใช้ "icons with text labels" และ "คนมักไม่กดสิ่งที่ไม่เข้าใจ" (NN/g Farrell 2015, R19) ⇒ กระดิ่ง/พระจันทร์เดี่ยว ๆ ในภาพ v0 ไม่ผ่านหลักนี้สำหรับกลุ่มเป้าหมาย
- ผู้ใช้สูงวัย: ปัญหาซ้ำทุกรอบวิจัยคือ ตัวเล็ก, ปุ่ม/ลิงก์เล็กเกินกด, ตัวอักษรสีจาง; ผู้สูงวัยทำผิดบ่อยกว่าและมักโทษตัวเอง → ข้อความ error ชัด อยู่ใกล้จุด และรับรูปแบบ input ยืดหยุ่น; ความสามารถใช้เว็บลดลง 0.8%/ปี ระหว่างอายุ 25–60 (NN/g Kane 2019, R20)
- ซ่อนเมนูหลัก (burger) บน desktop: ค้นพบลดลง >20%, เวลาทำงานนานขึ้น ≥39%, ความยากเพิ่ม 21% → "อย่าใช้ hidden navigation บน desktop" (NN/g Pernice & Budiu 2016, R21)
- เป้า target: WCAG 2.5.8 ขั้นต่ำ 24×24 CSS px, ควบคุมสำคัญแนะนำเกณฑ์เข้ม 2.5.5 (R22) — โปรเจกต์ใช้ 44 อยู่แล้ว (`standards/ui-ux.md` 2)
- reduced motion: ใช้ตาม `standards/ui-ux.md` 6.3 (MDN + WCAG 2.3.3) ไม่เปลี่ยน

**อนุมาน (ข้อเสนอเชิงออกแบบ)**
- เมนู: แสดงเฉพาะเมนูตามสิทธิ์ (มีแล้ว), กลุ่มหัวข้อ ≤4 กลุ่ม, ป้ายกลุ่มต้องเป็นภาษาคน (เช่น "งานของฉัน", "ข้อมูลหลักสูตร") — ภาพ v0 มี 5 กลุ่ม/10 รายการ + ป้ายกลุ่มตัวเล็กสีจาง → เพิ่มขนาด/contrast ป้ายกลุ่ม
- ความหนาแน่น: โหมด "สบายตา" เป็นค่าเริ่มต้น (แถวตาราง ≥48px, ช่องว่างการ์ด 24px), ปุ่มหลักต่อการ์ด 1 ปุ่ม, หน้าหนึ่งมีปุ่ม primary เด่นไม่เกิน 1–2
- ลูกเล่นที่ช่วย: feedback ทันทีหลังกด (สถานะปุ่มกำลังบันทึก → "บันทึกแล้ว ✓"), progress ring/แถบความคืบหน้าของรอบ SAR, ทักทายตามเวลา (มีแล้ว), เลข badge เด้งเบา ๆ ครั้งเดียวเมื่อมีใหม่, การ์ดยก 1–2px ตอน hover · ลูกเล่นที่รบกวน: animation วน/parallax/confetti เต็มจอ, toast หายเร็ว <5 วินาที, ทัวร์ onboarding บังจอหลายขั้น, tooltip-only — ทั้งหมดต้องปิดเมื่อ `prefers-reduced-motion: reduce`
- คำบนปุ่มเป็นกริยา + ผลลัพธ์ ("ส่งให้ประธานตรวจ" แทน "ส่ง")

### 5) ปุ่มภาษา + จัดกลุ่ม control ใน topbar
**ยืนยันแล้ว**
- **ไม่ใช้ธง**: ธงคือประเทศ ไม่ใช่ภาษา; ใช้ชื่อภาษาในภาษานั้นเอง (autonym) เช่น "ไทย", "English"; ผู้ใช้หาตัวเลือกภาษาที่ header ก่อน แล้ว footer; ไอคอนโลก/แปลภาษาช่วยให้หาเจอ ควรคู่กับข้อความ; **ตัวย่อ "EN" อาจถูกเบราว์เซอร์แปลอัตโนมัติจนสับสน** → ใช้ชื่อเต็มปลอดภัยกว่า; ห้าม auto-redirect ตามภาษาเบราว์เซอร์ (Friedman 2022, R23) · NN/g: ใช้ชื่อภาษาในอักษรของภาษานั้นแทนธง, วาง utility มุมขวาบน (R19)
- WCAG 3.1.2: ข้อความ "English" บนหน้าไทยต้องมี `lang="en"` (ตัวอย่าง W3C: "ข้อความลิงก์คือชื่อภาษาในภาษานั้น" + `lang`) (R24)
- Burger: desktop ห้ามซ่อนเมนูหลัก; mobile ถ้ามีเมนูหลัก ≤4 ให้แสดงตรง, มากกว่านั้นซ่อนบางส่วนได้ (R21) — AUN-QA มี ~10 เมนู → mobile (<1024) ใช้ drawer (มีแล้ว) ได้ แต่ปุ่ม burger ต้องมีคำว่า "เมนู"
- Utility ซ่อนหลังไอคอนเฟือง/burger "อาจย้อนผล ต้องทดสอบว่าคนหาเจอ" (R19)

**อนุมาน (ข้อเสนอ)**
- ปุ่มภาษา: segmented 2 ช่อง `ไทย | English` (ช่องที่เลือก = พื้น pri + ตัวหนา + `aria-pressed`/radio group), มีไอคอนโลก/文A นำหน้าเฉพาะ desktop; mobile ใช้ `ไทย | EN` ได้ถ้าที่ไม่พอ (EN ต้องมี `lang="en"` + `aria-label="English"`)
- การจัดกลุ่ม topbar desktop (≥1024): `[ไทย | English]` · `[กระดิ่ง + "แจ้งเตือน" + badge]` · `[avatar ชื่อ/บทบาท ▾]` — ย้าย **ธีม + ขนาดตัวอักษร + ภาษา(สำรอง)** ไปเมนู "การแสดงผล" (ใน avatar menu หรือปุ่ม "การแสดงผล" มีข้อความ) และ "ออกจากระบบ" ไปใน avatar menu ด้วย · ภาษาควรอยู่นอกเมนูเพราะคนที่อ่านภาษาปัจจุบันไม่ออกต้องหาเจอทันที (สอดคล้อง R23 "header first")
- mobile (<640): topbar = `[เมนู]` โลโก้ … `[กระดิ่ง]` `[avatar]`; ภาษา/ธีม/ขนาดตัวอักษร อยู่ใน drawer ส่วนท้าย + avatar menu
- ธีมใช้ 3 ทาง "สว่าง / มืดนุ่ม / ตามระบบ" แต่ **ค่าเริ่มต้น = สว่าง** (เจ้าของสั่ง; ตรงข้าม ADR-UI-002 ที่เลือก "ตามระบบ" → architect ต้องแก้)

## อนุมาน / ยังไม่แน่ใจ
- ตัวเลข contrast ผ่านหมด แต่ "สวย/อบอุ่นพอดี" ตัดสินด้วยตา → ui-inspector ต้อง render บนจอจริง (และ grayscale ตาม AC-07) ก่อนล็อก
- terracotta (E1) เป็นสีแดงอมส้ม: ผู้ใช้บางคนอาจรู้สึกเป็น "เตือน/ผิดพลาด" — [อนุมาน] ถ้าเจ้าของกังวล ใช้ E2/E3 ที่สีหลักเป็นเขียว และใช้ดินเผาเป็นแค่ accent
- ระบบความปลอดภัยใน localStorage เป็น **การจำลอง**: ทุกอย่างอยู่ใน browser → ผู้ใช้ที่เปิด DevTools แก้ role/โทเคนได้เอง; การตรวจสิทธิ์ใน `lib/api` ป้องกันเฉพาะผ่าน UI. เล่มต้องเขียนเป็นข้อจำกัด (ไม่ใช่ข้ออ้างว่าปลอดภัยจริง)
- PDPA ม.21–23 เป็นแหล่งรอง; ระยะเวลาลบคำขอที่ถูกปฏิเสธ (เช่น 30 วัน) เป็นข้อเสนอ ไม่มีตัวเลขในกฎหมายที่ยืนยัน
- รหัสผ่านขั้นต่ำ 15 (NIST) อาจหนักสำหรับผู้ใช้กลุ่มนี้ — ทางสายกลางที่สอดคล้อง NIST: ขั้นต่ำ ≥8 ถ้าวันหน้ามี MFA; ใน MVP ไม่มี MFA ⇒ ตามตัวอักษร NIST ต้อง 15 → ให้ architect/เจ้าของตัดสิน (อย่างน้อยเลิกจำกัด 6 และห้ามกฎผสมอักขระ)
- NIST 800-63B-4 ส่วน enrollment/activation code (§4) ยังไม่ได้อ่าน (หน้ายาวเกิน) — อายุลิงก์เชิญ 7 วันเป็นข้อเสนอ
- ไม่ได้เปิดหน้า Material dark theme spec (m2/m3 เปิดไม่ได้), Apple HIG (เนื้อหาไม่โหลด), Visa notification tray (ถูกตัด), ASVS 5.0 ตัวเต็ม

## ข้อแนะนำต่อ architect
1. **Onboarding = O1 (ขั้นต่ำ) หรือ O2 (ถ้าต้องการหน้า "ขอเข้าใช้งาน")** · คำเชิญเก็บ: `tokenHash`, role+scope (กำหนดโดยผู้เชิญ), `invitedBy`, `expiresAt` (เสนอ 7 วัน), `usedAt`; token จาก `crypto.getRandomValues` ≥128 bit, ใช้ครั้งเดียว, หน้า accept ตอบข้อความเดียวกันทั้งกรณีหมดอายุ/ไม่มี/ใช้แล้ว (R5) · ฟอร์ม accept/ขอเข้าใช้ ใช้ allowlist ฟิลด์ (ไม่มี role) (R2) · คำขอใน O2: เก็บเฉพาะชื่อ อีเมล หน่วยงาน ตำแหน่ง + ข้อความแจ้งวัตถุประสงค์ (PDPA ม.22–23 แหล่งรอง) + ลบคำขอที่ปฏิเสธหลังระยะที่กำหนด · รหัสผ่าน: ยกเลิกขั้นต่ำ 6 ตัว ให้ตาม NIST (≥15 ถ้าไม่มี MFA หรือบันทึกเหตุผลถ้าเลือก 8) ไม่บังคับผสมอักขระ, รองรับยาว ≥64 (R6) — **เรื่องนี้แตะ `lib/api` → ต้องแก้ AC-20 หรือแตก subtask backend**; ต้องเขียน ADR onboarding
2. **Notification panel**: ปุ่มกระดิ่งมีข้อความ "แจ้งเตือน" (desktop) + badge นับ unread (`99+`), `aria-expanded`/`aria-controls`, label รวมจำนวน; popover desktop / sheet เต็มจอ mobile; หัว panel: ชื่อ + "อ่านทั้งหมด"; รายการใหม่→เก่า จัดกลุ่ม วันนี้/เมื่อวาน/ก่อนหน้า, unread = ตัวหนา + จุดสี + คำ "ใหม่" (ไม่พึ่งสี), เวลาสัมพัทธ์ <1 ชม.; กด = mark read + นำทาง deep link ตาม kind + ปิด panel; empty state; เรื่องต้องทำทันทียังอยู่ใน "สิ่งที่ต้องทำ" ของหน้าหลัก (R11, R12) และเอากล่อง "แจ้งเตือน" ออกจากหน้าหลัก; EN ต้องมีข้อความแปลตาม kind (มีแค่ `messageTh`)
3. **Palette**: เสนอเจ้าของเลือก E1/E2/E3 (หรือให้ ui-inspector ทำภาพเทียบ 3 ชุด) — researcher เอนไป **E2 หรือ E3** (สีหลักเขียวไม่ชนความหมาย error) โดยใช้ดินเผาเป็น accent; ล็อกค่าลง `saas-tokens.md` §T1/§T2 ใหม่ แล้ว `tests/contrast.test.ts` ต้องวัดคู่ใหม่ทั้งหมด · โหมดมืด = warm dim ตามตาราง (ห้าม `#000`, ห้าม ink `#FFF`) · ค่าเริ่มต้นธีม = **สว่าง** (แก้ ADR-UI-002/AC-13 ข้อ 3)
4. **Topbar**: `[ไทย | English]` segmented (autonym + `lang="en"`, ไม่ธง, ไม่ auto-redirect) · `[กระดิ่ง แจ้งเตือน]` · `[avatar ▾]` ข้างในมี "การแสดงผล" (ธีม 3 ทาง + ขนาดตัวอักษร ก-/ก/ก+) และ "ออกจากระบบ" — ลดไอคอนเดี่ยวเหลือ 0 บน desktop · sidebar คงแสดงตลอดบน desktop (ไม่ burger) · mobile ใช้ drawer + ปุ่ม "เมนู" มีข้อความ
5. **ความเป็นมิตร**: ทุกไอคอนมีข้อความ (ยกเว้นในตารางแน่น ใช้ `aria-label` + tooltip เสริม), ≤4 กลุ่มเมนู, 1 ปุ่ม primary ต่อการ์ด, ลูกเล่นแบบ feedback/progress เท่านั้น และปิดด้วย reduced-motion; เพิ่ม AC วัด "ไม่มีปุ่มไอคอนเดี่ยวไม่มีข้อความที่มองเห็นใน topbar/sidebar desktop"
6. ใส่ข้อจำกัด "ความปลอดภัยแบบจำลองใน localStorage" ใน Log ให้ thesis-writer (บทที่ 5 ข้อจำกัด/ข้อเสนอแนะ: ย้ายไป Supabase invite + SSO โดเมนมหาวิทยาลัย)
