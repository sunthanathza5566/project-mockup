## 1. NIST SP 800-63B-4 / 800-63A-4 (ฉบับ final, ก.ค. 2025)

### 1.1 รหัสผ่าน — SP 800-63B-4 §3.1.1.2 Password Verifiers [ต้นฉบับ]
| # | ข้อกำหนด | ระดับ | ผลกับระบบนี้ |
|---|---|---|---|
| N1 | รหัสผ่านที่ใช้เป็น **ปัจจัยเดียว** ต้องยาว ≥ **15** ตัว; ถ้าใช้เป็นส่วนของ MFA ขั้นต่ำ **8** ตัว (item 1) | SHALL | ระบบใช้ 8 โดยไม่มี MFA → **ไม่ผ่าน** — เจ้าของเลือก 8 (ADR-AUTH-001 §ความปลอดภัย) ⇒ ต้องเขียนเป็นข้อจำกัด/deviation ในเล่ม |
| N2 | ควรยอมรับความยาวสูงสุด ≥ **64** ตัว (item 2) | SHOULD | `PASSWORD_MAX = 128` → ผ่าน |
| N3 | **ห้าม** กฎผสมชนิดอักขระ (item 5) | SHALL NOT | ADR ห้ามแล้ว → ตรวจว่าไม่มี regex บังคับตัวใหญ่/ตัวเลข |
| N4 | **ห้าม** บังคับเปลี่ยนรหัสตามรอบเวลา (เปลี่ยนเมื่อถูกเปิดเผยเท่านั้น) (item 6) | SHALL NOT | ไม่มีฟีเจอร์นี้ → ผ่าน |
| N5 | **ห้าม** เก็บ "คำใบ้รหัสผ่าน" ที่ผู้ไม่ได้ยืนยันตัวตนเห็นได้ (item 7) | SHALL NOT | ไม่มี → ผ่าน |
| N6 | ต้องเทียบรหัสที่ตั้งใหม่กับ **blocklist** รหัสที่ใช้บ่อย/คาดเดาได้/รั่ว; ไม่ผ่าน → ให้เลือกใหม่ | SHALL | **ยังไม่ทำ** → ข้อจำกัด/งานอนาคต |
| N7 | Appendix A: blocklist **ไม่ควรใหญ่เกินไป** (ผู้ใช้จะหงุดหงิด) | แนวทาง | ถ้าทำในอนาคต: ใช้ชุดเล็ก (เช่น top 3,000 ตาม ASVS 6.2.4) |

### 1.2 จำกัดการลองผิด — §3.2.2 Rate Limiting [ต้นฉบับ]
- N8 ต้องจำกัดการยืนยันตัวตนผิดติดกันต่อ authenticator ต่อบัญชี **ไม่เกิน 100 ครั้ง**; 100 เป็นเพดาน หน่วยงานกำหนดต่ำกว่าได้ (SHALL/MAY)
- ระบบนี้: `MAX_ATTEMPTS = 5` + ล็อก 5 นาที (`eduflow-next/lib/api/auth.api.ts:18-19`) → ผ่าน (เข้มกว่า) · ADR: บัญชี `invited` ที่ login ต้องนับครั้งผิดเหมือนรหัสผิด → ตรวจใน 4.x

### 1.4 Enrollment / confirmation code — SP 800-63A-4 [ต้นฉบับ]
- คำว่า "enrollment code" **ไม่มี** ในฉบับ -4 แล้ว — แทนด้วย **confirmation code** (§3.8, ยืนยันว่าผู้สมัครเข้าถึงที่อยู่/อีเมล/โทรศัพท์ได้): ≥ 6 หลักทศนิยม (หรือเทียบเท่า) จาก approved RBG; อายุสูงสุด **21 วัน** (ไปรษณีย์ในสหรัฐฯ) / **30 วัน** (นอก) / **10 นาที** (SMS/เสียง) / **24 ชั่วโมง** (อีเมล)
- **Continuation code** (§3.9, ให้ผู้สมัครกลับมาทำ proofing ต่อ): ≥ 64 bit, "expiry is not defined in these guidelines"
- Notification of proofing (§3.10): ต้องแจ้งผลการพิสูจน์ตัวตนไปยังที่อยู่ที่ยืนยันแล้ว (IAL1 ใช้อีเมลได้)
- เลข section ของ 800-63A-4 ได้จากการไล่ลำดับหัวข้อ + cross-reference ในหน้า HTML ("Sec. 3.8") — HTML ไม่แสดงเลขหัวข้อตรง ๆ → **ยืนยันระดับปานกลาง** (เปิด PDF DOI เทียบได้ถ้าต้องอ้างในเล่ม)

### 1.5 อายุลิงก์เชิญที่ "แนะนำ" — สรุปของ researcher
- **NIST ไม่มีข้อกำหนดชื่อ "invitation link" ตรง ๆ** [ต้นฉบับ — ไม่พบใน 63A-4/63B-4] ⇒ ต้องเทียบเคียง [อนุมาน]:
  - ลิงก์เชิญ = ความลับใช้ครั้งเดียวที่ทำให้ผู้ถือ "ตั้งรหัสผ่านแรก" ของบัญชีที่ผู้ดูแลสร้างไว้ → ใกล้ที่สุดคือ issued recovery / confirmation code ที่ส่งทาง **อีเมล = ≤ 24 ชม.** (N11, 1.4) และ ASVS 6.4.1 "expire after a short period of time"
  - ADR-AUTH-001 ตั้ง `INVITE_TTL_MS = 7 วัน` → **ยาวกว่าเพดานที่เทียบเคียงของ NIST (24 ชม.)**
  - ข้อชดเชยที่ ADR มีแล้ว: 256 bit จาก CSPRNG (> 112 bit N9), เก็บเฉพาะ hash, ใช้ครั้งเดียว, revoke ได้, ข้อความ error เดียว, ไม่มีอีเมลจริง (admin ส่งเองนอกระบบ)
- ข้อเสนอ [อนุมาน]: (a) คง 7 วันได้ในเดโม่ **แต่ต้องบันทึกเป็น deviation พร้อมเหตุผล** (ส่งด้วยมือ ผู้ใช้วัยกลาง–สูงอาจไม่เปิดทันที, มีปุ่ม "ออกลิงก์ใหม่") หรือ (b) ลดเป็น 72 ชม./24 ชม. ถ้าจะอ้างว่า "สอดคล้อง NIST" — ห้ามเขียนในเล่มว่า 7 วัน "ตาม NIST"

### 3.3 Checklist ข้อมูลผู้ขอใช้งาน (ฟอร์ม "ขอเข้าใช้งาน") [อนุมานจาก 3.2]
- P1 (ม.22) ฟิลด์ = ชื่อ, อีเมลสถาบัน, username, รหัสผ่าน, หลักสูตร/คณะ, ตำแหน่ง (ข้อความ), เหตุผล — **ไม่มี** เลขบัตร/โทรศัพท์/วันเกิด/รูป; ทุกฟิลด์มีเหตุผลใช้งาน (อนุมัติ/กำหนด role)
- P2 (ม.23) ข้อความแจ้งบนฟอร์ม **ก่อนกดส่ง** มีครบ 6 ข้อ: วัตถุประสงค์ (พิจารณาให้สิทธิ์ใช้งาน), ผลถ้าไม่ให้ข้อมูล (ขอใช้งานไม่ได้), ข้อมูลที่เก็บ + **ระยะเก็บ** (เช่น ถูกปฏิเสธ = ลบทันที; อนุมัติ = ตลอดอายุบัญชี; audit = ระบุ), ผู้ที่เห็นข้อมูล (ผู้ดูแลระบบของมหาวิทยาลัย), ช่องทางติดต่อ, สิทธิของเจ้าของข้อมูล
- P3 (ม.21) ใช้ข้อมูลคำขอเฉพาะการพิจารณา/ดูแลบัญชี — ไม่นำไปแจ้งเตือนอื่น/ส่งออก/ใช้กับ AI โดยไม่แจ้งใหม่
- P4 (ม.19 vs ม.24) [อนุมาน — ควรให้ที่ปรึกษากฎหมาย/อาจารย์ยืนยัน] ฐานที่เหมาะกับคำขอใช้งานคือ **ม.24(3) ดำเนินการตามคำขอของเจ้าของข้อมูล** หรือ ม.24(4)/(5) ไม่ใช่ "ความยินยอม" — checkbox ใน ADR (`consent === true`) จึงควรเรียก/เขียนว่า **"รับทราบประกาศความเป็นส่วนตัว"** มากกว่า "ยินยอม" (ถ้าใช้ฐานความยินยอม ม.19 กำหนดเรื่องถอนได้ง่ายและห้ามผูกเงื่อนไข ซึ่งขัดกับการที่ไม่ติ๊กแล้วส่งไม่ได้)
- P5 (ม.23(3) + ASVS 14.2.7) คำขอถูกปฏิเสธ → ลบแถวทันที (ADR ทำแล้ว) · คำขอที่ค้างนานควรมีระยะลบ (งานอนาคต)
- P6 ข้อมูลทดสอบ/seed ใช้ชื่อปลอมเท่านั้น (PROTOCOL)
