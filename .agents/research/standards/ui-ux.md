## 0. สภาพธีมปัจจุบัน (จุดที่ต้องแก้ — หลักฐานจากโค้ด)
- ฟอนต์หลักคือ `DM Sans` + `Cormorant Garamond` โหลดจาก Google Fonts พร้อม `Sarabun` (`eduflow-next/app/layout.tsx:20`); `globals.css:27` ตั้ง body เป็น DM Sans. - ตัวอักษรเล็ก: `.dash-kpi-label` 0.75rem (12px), `.dash-user-role` 0.72rem, `.section-label` 0.72rem, `.auth-label` 0.75rem, `.auth-sub` 0.78rem, `.dash-tab-btn` 0.8rem (`globals.css:79,157,150,172,179,181`) → ต่ำกว่าเกณฑ์ข้อ 1 ทั้งหมด
- `text-transform: uppercase` + `letter-spacing` กว้างบน label/nav (`globals.css:54,79,157`) — ไม่มีผลกับอักษรไทยแต่ทำให้ label ภาษาอังกฤษอ่านยากและไม่สม่ำเสมอสองภาษา **[อนุมาน]**

## 1. ตัวอักษร + ภาษาไทย (checklist)

### 1.1 กฎที่นำไปใช้ทันที
- [ ] **เนื้อหา/ฟอร์ม/ตาราง ≥ 16px (1rem)**; ข้อความช่วย/คำอธิบายย่อย ≥ 14px (0.875rem); **ห้ามมีข้อความอ่านเนื้อหาต่ำกว่า 14px** (badge ตัวเลข/ป้ายสั้นไม่น้อยกว่า 13px และต้องไม่ใช่ข้อมูลหลัก). ที่มา: ผู้สูงวัยไทยในงานวิจัยชอบ 16 pt; คนไทยวัยหนุ่มสาว ≥14 pt **[ยืนยัน]** (ข้อ R1); NN/g: ข้อความเล็ก/จางเป็นปัญหาซ้ำในทุกการศึกษา และสายตาเสื่อมเริ่มตั้งแต่อายุ 40 ต้น ๆ **[ยืนยัน]** (R2)
- [ ] หน่วยเป็น `rem` ทั้งหมด ห้ามตรึง `px` กับขนาดตัวอักษร; layout ต้องไม่แตกเมื่อผู้ใช้ขยายข้อความ 200% (WCAG 1.4.4) **[ยืนยัน]** (R3)
- [ ] **line-height เนื้อหาไทย 1.6–1.75** (หัวข้อ ≥1.35): ภาษาไทยเป็นสคริปต์ "สูง" (สระ/วรรณยุกต์บน-ล่าง) ต้องเผื่อบรรทัด **[ยืนยันในแหล่งรอง]** (R4) — ค่าตัวเลข 1.6–1.75 เป็น **[อนุมาน]** (ไม่พบแหล่งที่วัดต่อฟอนต์; โค้ดเดิมใช้ 1.7 ที่ `globals.css:267` และผ่านการใช้งานแล้ว) → ให้ ui-inspector ตรวจภาพจริงที่หัวข้อที่มีวรรณยุกต์ซ้อนสระบน (เช่น "ที่ปรึกษา", "ผู้ใช้") ว่าไม่ถูกตัด
- [ ] ผลต้องไม่พังเมื่อผู้ใช้บังคับ line-height 1.5, paragraph 2×, letter 0.12em, word 0.16em (WCAG 1.4.12) **[ยืนยัน]** (R5) → ห้ามกำหนดความสูงคงที่ให้กล่องที่มีข้อความ ใช้ `min-height` แทน
- [ ] ความกว้างบรรทัดอ่านยาว ~ 60–75 ตัวอักษรละติน หรือ `max-width: 42rem`–`46rem` **[อนุมาน]**; ย่อหน้า **ชิดซ้าย** ห้าม justify/center ข้อความยาว (W3C WAI older users C19) **[ยืนยัน]** (R6) — ภาษาไทยไม่มีช่องว่างระหว่างคำ ถ้าใช้ justify จะเกิดช่องไฟเพี้ยน **[อนุมาน]**
- [ ] ห้ามใช้ `uppercase`/`letter-spacing` เกิน 0.02em กับข้อความที่อาจเป็นภาษาไทย; ห้ามใช้ตัวเอียงยาว (R6) **[ยืนยันส่วนตัวเอียง / อนุมานส่วนไทย]**
- [ ] น้ำหนักฟอนต์เนื้อหา 400 (ไม่ใช้ 300 กับไทยขนาดเล็ก — เส้นบางทำให้วรรณยุกต์จาง **[อนุมาน]**); ข้อความเน้น 600; หัวข้อ 600–700
- [ ] แยกชั้น: หัวข้อ/ตัวเลขใหญ่ใช้ขนาด+น้ำหนักสร้างลำดับ ไม่ใช้สีอ่อนสร้างลำดับ (muted ต้องผ่าน 4.5:1 เสมอ)
- [ ] ให้ผู้ใช้ปรับขนาดตัวอักษรได้ (ปุ่ม ก- / ก / ก+ ในเมนูผู้ใช้ เก็บค่าใน localStorage, ปรับ `html{font-size}` เป็น 100% / 112.5% / 125%) — ทำด้วย CSS ตัวแปร + JS ไม่กี่บรรทัด ไม่ต้องใช้ lib. เหตุผล: ผู้ใช้ 50–60+ ต่างกันมาก และ W3C แนะนำตัวควบคุมขยายข้อความ (G178) **[ยืนยัน R6; การเลือกนำมาใช้ = ข้อเสนอ]**

### 1.2 เปรียบเทียบฟอนต์ไทย (สำหรับตัดสินใจ — ข้อมูลจำกัด ระบุตรง ๆ)
ไม่พบงานทดสอบความอ่านง่ายหัวต่อหัวของ 4 ฟอนต์นี้ (ค้นแล้ว: R4) หน้าสเปก Google Fonts เปิดไม่ได้ (โหลดด้วย JS ได้แต่ชื่อหน้า) → ตารางด้านล่างเป็น **[อนุมาน]** ทั้งหมด จากหมวดฟอนต์ที่บล็อกปฏิบัติจัดกลุ่ม (Sarabun/IBM Plex Sans Thai = humanist; Noto Sans Thai/Anuphan = minimal) และความรู้ทั่วไป; ต้องให้ ui-inspector ทดลอง render จริงก่อนล็อก

| ฟอนต์ | ลักษณะ | จุดแข็ง | ข้อควรระวัง |
|---|---|---|---|
| **Sarabun** | humanist, มีหัว (loop) ชัด สไตล์ใกล้ TH Sarabun ที่ราชการ/วิชาการไทยคุ้นตา | อ่านง่ายที่ขนาดเล็ก, **คุ้นตาผู้ใช้ 40–60+**, อยู่ใน repo แล้ว (`layout.tsx:20`, และ DOCX ใช้ TH Sarabun New `phase-c1.test.ts:622`) → เอกสารกับเว็บรู้สึกต่อเนื่อง; ถ้าเลือกทำให้ **ไม่ต้องเพิ่มฟอนต์ใหม่** | ดู "ราชการ" ถ้าไม่จับคู่กับหัวข้อที่มีบุคลิก; มีละตินของตัวเอง ควรตรวจว่าตัวเลข/อังกฤษดูกลมกลืน |
| **IBM Plex Sans Thai** | humanist/geometric เล็กน้อย มีทั้งแบบมีหัว/ไม่มีหัว (แหล่ง R4: "performs well at small sizes" — เป็นเว็บ SEO คุณภาพต่ำ) | ดูทันสมัยกว่า, ละตินคู่ IBM Plex Sans เข้าชุด, ตัวเลขชัด (เหมาะ dashboard) | เป็นฟอนต์ใหม่ต้องโหลดเพิ่ม (1 family); ยังไม่ยืนยันว่ามีกี่ weight |
| **Noto Sans Thai** | minimal sans ครอบคลุมทุกน้ำหนัก | กลาง ๆ เป็นกลาง ใช้ fallback ได้ทุกเครื่อง | จืด/แข็ง ขัดโจทย์ "ไม่น่าเบื่อ"; ไทยแบบไม่มีหัวอาจลดความคุ้นตาผู้สูงวัย **[อนุมาน]** |
| **Anuphan** | minimal sans รูปร่างมีบุคลิก | ดูร่วมสมัย | ใหม่ ผู้ใช้สูงวัยอาจคุ้นน้อย; ไม่พบข้อมูลวัดความอ่าน |

**ข้อมูลที่มีน้ำหนักที่สุดข้อเดียว (R1):** ผู้ใช้เว็บไทย (รวมผู้สูงวัย) ชอบฟอนต์ไทยแบบ "conservative" ซึ่งใกล้ serif/มีหัวชัด **[ยืนยัน]** — ทิศทางนี้ **สนับสนุน Sarabun** (และ IBM Plex Sans Thai แบบมีหัว) มากกว่า minimal sans. ขอบเขตงานวิจัยนี้ทดสอบ Arial/Times/ฟอนต์ไทย conservative ไม่ได้ทดสอบ 4 ฟอนต์นี้ จึงเป็นการ "ชี้ทิศทาง" ไม่ใช่ผลวัด
**ข้อเสนอ:** body/UI = **Sarabun** (ไทย+อังกฤษ); หัวข้อ/ตัวเลขเด่นเพิ่มบุคลิกได้ด้วย IBM Plex Sans Thai หรือ Sarabun น้ำหนัก 700 (architect เลือก). ทิ้ง Cormorant Garamond ที่ไม่มีกลิฟไทย (หรือเก็บไว้เฉพาะโลโก้/หน้า landing ภาษาอังกฤษ). ใช้ `display=swap` และ preload ได้ด้วย `next/font` หรือ `<link>` เดิม — **ไม่เพิ่ม dependency** (next/font เป็นส่วนของ Next อยู่แล้ว **[อนุมาน]** ว่าเวอร์ชันที่ใช้รองรับ; ถ้ากลัว ให้คง `<link>` เดิม)

## 2. Target size + การโต้ตอบ
- [ ] **ขั้นต่ำ WCAG 2.2 AA (SC 2.5.8): 24×24 CSS px** (ยกเว้น: spacing, inline ในประโยค, ฯลฯ) **[ยืนยัน]** (R7)
- [ ] **ตั้งเกณฑ์ของโปรเจกต์ที่เข้มกว่า: ปุ่ม/ช่องกรอก/แถวที่คลิกได้สูง ≥ 44px (เดสก์ท็อปอย่างน้อย 40px), ไอคอนล้วนต้องมีพื้นที่กด ≥ 44×44 รอบ ๆ** — 44 มาจาก SC 2.5.5 AAA (ที่ R7 อ้างถึงแต่ไม่ได้ระบุตัวเลข) และ NN/g ที่ว่าเป้าเล็กเกินไปเป็นปัญหาของผู้สูงวัย (R2) → ตัวเลข 44 = **[อนุมาน จากความรู้ทั่วไป ไม่ได้เปิดหน้า 2.5.5]** ให้ architect ถือเป็นเกณฑ์ออกแบบ
- [ ] ระยะห่างระหว่างปุ่มที่ติดกัน ≥ 8px (ลดกดผิด; ปุ่มทำลาย เช่น ลบ ต้องแยกห่างจากปุ่มหลัก ≥ 16px และยืนยันก่อน)
- [ ] ปุ่มมีข้อความ (ไม่ใช่ไอคอนล้วน) สำหรับการกระทำหลัก; ไอคอนล้วนต้องมี `aria-label` + tooltip
- [ ] **Focus ring มองเห็นชัดเสมอ** (WCAG 2.4.7; W3C older users) **[ยืนยัน]** (R6): `outline: 3px solid <primary>; outline-offset: 2px` (contrast ≥3:1 กับพื้นข้างเคียง) ห้าม `outline:none` โดยไม่ทดแทน; รองรับคีย์บอร์ดครบ ไม่มี keyboard trap
- [ ] รับอินพุตหลายรูปแบบ ไม่บังคับ date picker อย่างเดียว ให้พิมพ์ได้ และยอมรับขีด/วงเล็บ/ช่องว่างในเบอร์โทร (NN/g) **[ยืนยัน]** (R2)
- [ ] ไม่เปลี่ยน context เมื่อแค่โฟกัส; เปิดหน้าต่างใหม่เฉพาะเมื่อผู้ใช้สั่ง; บอกตำแหน่งปัจจุบันใน nav (`aria-current`) + breadcrumbs (R6) **[ยืนยัน]**
- [ ] ภาษาง่าย: ศัพท์ AUN-QA/เกณฑ์ ให้มีคำอธิบายสั้น (tooltip/"?" ในบริบท) ไม่ใช้ศัพท์ระบบ/อังกฤษล้วนเป็นปุ่ม; ใช้คำกริยาบอกผล เช่น "บันทึกร่าง" แทน "Submit" (R6: ภาษาง่าย, อธิบายตัวย่อ) **[ยืนยัน หลักการ]**

## 3. Contrast (WCAG 2.2 AA)
เกณฑ์ **[ยืนยัน]** (R8 + R6): ข้อความปกติ ≥ **4.5:1**; ข้อความใหญ่ (≥18pt หรือ ≥14pt ตัวหนา ≈ 24px / 18.66px) ≥ **3:1**; ส่วนประกอบ UI/กราฟิกที่จำเป็น (ขอบช่องกรอก, ไอคอนสถานะ, focus ring) ≥ **3:1** (SC 1.4.11 — ตัวเลข 3:1 ไม่ได้ระบุตรงในหน้าที่เปิด จึงยืนยันบางส่วน; เป็นเกณฑ์ที่ทราบกันทั่วไป) · **ข้อเสนอโปรเจกต์:** ข้อความเนื้อหาไทยเป้าหมาย ≥ 7:1 สำหรับ ink และ ≥ 4.5:1 ทุกสี (muted ต้องไม่ต่ำกว่า 4.5:1 — สีจางเป็นปัญหาผู้สูงวัย R2)
- [ ] ห้ามพื้น `#FFF` ล้วนขนาดใหญ่ + ตัว `#000` ล้วน (แสงจ้า) — ใช้พื้นอุ่น/เย็นนวล (`bg`) + ตัว ink เข้มไม่ดำสนิท (R6 แนะ "หลีกเลี่ยงขั้วสุดโต่ง พื้นพาสเทลได้") **[ยืนยัน]**
- [ ] ข้อความบนปุ่มสีหลัก/สถานะ ตรวจเป็นคู่ ๆ ทุกคู่ในตารางของแต่ละ palette (ด้านล่าง)
- [ ] ข้อความ placeholder ต้อง ≥4.5:1 ด้วย และห้ามใช้แทน label
- [ ] ลิงก์ในเนื้อหาต้องมีขีดเส้นใต้หรือสัญญาณอื่นนอกจากสี (R6: 1.4.1)

## 4. Palette: สบายตาแต่มีชีวิต

### 4.1 หลักเลือกสี
- ฐานสว่างนวล (ไม่ขาวจ้า) + ผิว card ขาว สร้างมิติเบา ๆ แทนเงาหนัก **[อนุมาน เชิงออกแบบ; ส่วน "หลีกเลี่ยงสุดขั้ว" ยืนยัน R6]**
- **สีหลักหนึ่งสี (เข้ม อ่านตัวขาวบนปุ่มได้ ≥4.5:1)** + **สีเน้นหนึ่งสี (อุ่น สดกว่า)** ใช้เฉพาะจุด: ปุ่มรอง, highlight ความคืบหน้า, ภาพประกอบ, "ฉลอง". อัตราส่วนใช้ ประมาณ 60 พื้น/30 ผิว-ข้อความ/10 สีหลัก+เน้น **[อนุมาน กฎ 60-30-10 ทั่วไป]**
- "ไม่จืด" = ใส่สี tint ของสีหลักที่พื้นส่วนหัว/การ์ดเด่น, ไล่สีบาง ๆ (subtle gradient) ที่ hero/โปรไฟล์/progress, ภาพประกอบเส้น (inline SVG), ไอคอนมีสีเน้น — ไม่ต้องใช้สีสดเต็มหน้า
- "ไม่สดเกิน" = สีหลักมี saturation ปานกลาง, ไม่ใช้สีนีออน/แดงสดเป็นพื้นใหญ่, สีเน้นใช้ ≤10% ของพื้นที่
- **สีสถานะ ต้องไม่พึ่งสีอย่างเดียว (WCAG 1.4.1 — R6) [ยืนยัน]:** ทุกสถานะ = สี + **ไอคอนรูปทรงต่างกัน** + **ข้อความ** (✓ สำเร็จ / ⚠ รอตรวจ/เตือน / ✕ ผิดพลาด / ⓘ ข้อมูล / ● ร่าง). แถบ error ในฟอร์ม = กรอบสีแดง + ข้อความ + คำนำ "ข้อผิดพลาด:" ให้ screen reader (GOV.UK error-message **[ยืนยัน]** R9)
- สีบอด: แยกเขียว-แดงยากที่สุด ห้ามใช้คู่นี้เป็นตัวบอกเดียว; ควรให้คู่สีที่ต่างด้วย **ความสว่าง** ไม่ใช่เฉพาะเฉดสี; ใช้ "bluish green", "vermilion" แทนเขียวสด/แดงสด และสลับโทนอุ่น-เย็น (Okabe–Ito / Ito & Okabe, R10) **[ยืนยัน]**; ใส่ป้ายตรงในกราฟแทนคำอธิบายสีแยก; ไม่ใช้แดงบนพื้นดำ
- ข้อมูลกราฟ/ชุดข้อมูลหลายซีรีส์ ให้ใช้ชุดสี Okabe–Ito ปรับความสว่างเอง + ลาย (เส้นประ/รูปจุด) ตามหลัก "อย่าส่งข้อมูลด้วยสีอย่างเดียว" (R10). *หมายเหตุ: หน้า R10 ไม่ระบุค่า hex ของพาเลต (อยู่ในภาพ) จึงไม่ลอกค่ามา*

## 5. Loading / Skeleton / Empty / Error / Success states

### 5.1 Loading (NN/g R11, R12)
- [ ] ตอบสนองทันทีเมื่อกด (สถานะ pressed/disabled+ข้อความ "กำลังบันทึก…") ภายใน 100 ms — กันกดซ้ำ ไม่ต้องใช้ข้อความ "อย่ากดซ้ำ" **[ยืนยัน]**
- [ ] < 1 วินาที: **ไม่แสดงอะไร** (ไม่ flash skeleton) → ทำ delay 300–400 ms ก่อนค่อยแสดง skeleton **[ยืนยันหลักการ R11; ตัวเลข 300–400 ms = อนุมาน]**
- [ ] 2–10 วินาที: skeleton สำหรับทั้งหน้า/spinner สำหรับโมดูลเดียว + ข้อความ ("กำลังโหลดรายการหลักสูตร…") **[ยืนยัน]**
- [ ] > 10 วินาที (เช่น AI ร่าง SAR, export DOCX, import Excel): **แถบความคืบหน้าแบบทีละขั้น** ("ขั้นที่ 2 จาก 4: วิเคราะห์หลักฐาน") + บอกเวลาคร่าว ๆ + ปุ่มยกเลิกถ้าทำได้ **[ยืนยัน]** — งานแบบ process ใช้ progress bar/wizard ไม่ใช้ skeleton (R11)
- [ ] skeleton ต้องสะท้อนโครงจริง (การ์ด/แถวตาราง) ไม่ใช่แค่หัว-ท้าย (R11) ใช้ CSS gradient เลื่อน (`background-position` animation ~1.4s) ปิดเป็นสีนิ่งเมื่อ reduced-motion
- [ ] หน้า Loading ระดับแอป/หน้า login/logout ใช้ธีมเดียวกับระบบ (โลโก้ + ข้อความสั้น) ห้ามคนละธีม (ปัญหาที่เจ้าของระบุ); ห้ามหมุนไม่จบโดยไม่มี timeout → แสดง "ใช้เวลานานกว่าปกติ ลองใหม่" หลัง ~10 s

### 5.2 Empty state (NN/g R13) **[ยืนยัน]**
- [ ] บอกสาเหตุ/สถานะ (ไม่ว่างเปล่า, ไม่แสดง "ไม่มีข้อมูล" ระหว่างที่ยังโหลด)
- [ ] สอนว่าฟีเจอร์นี้ทำอะไร + ทำอย่างไรให้มีข้อมูล (1–2 ประโยค ภาษาง่าย)
- [ ] มีปุ่มทำต่อทันที ("เพิ่มหลักฐานชิ้นแรก", "นำเข้าจาก Excel") และลิงก์คู่มือ
- [ ] ภาพประกอบเส้นเบา ๆ (inline SVG) ใช้สีเน้นได้ — เพิ่มความมีชีวิตโดยไม่รบกวน

### 5.3 Error (GOV.UK R9; NN/g R2) **[ยืนยัน]**
- [ ] บอก "เกิดอะไร + แก้อย่างไร" ภาษาธรรมดา ไม่โทษผู้ใช้ ("ไม่พบไฟล์ที่เลือก ลองเลือกไฟล์ .xlsx อีกครั้ง" ไม่ใช่ "คุณกรอกผิด")
- [ ] วางข้อความถัดจากช่องที่เกี่ยวข้อง + กรอบแดง + ไอคอน + สรุปข้อผิดพลาดรวมบนหัวฟอร์มพร้อมลิงก์ไปยังช่อง; ไม่ล้างข้อมูลที่กรอกแล้ว
- [ ] เลี่ยงคำกำกวม ("Invalid", "ไม่ถูกต้อง" เฉย ๆ), ข้อความทั่วไป ("เกิดข้อผิดพลาด"), ข้อความตลก
- [ ] ระดับระบบ (เครือข่าย/เซิร์ฟเวอร์) ใช้แถบบนสุดที่ปิดได้ + ปุ่ม "ลองอีกครั้ง" ไม่ใช้ alert()
- [ ] ปัญหาสิทธิ์/ขอบเขต (ไม่มีสิทธิ์) ใช้หน้าอธิบายพร้อมทางไปต่อ ไม่ใช้ข้อความฟอร์ม (R9)

### 5.4 Success / ยืนยัน
- [ ] Toast สำเร็จ 4–6 วินาที (ผู้สูงวัยอ่านช้า — ไม่ใช้ 2 s) มีปุ่มปิด + `role="status"`/`aria-live="polite"`; การกระทำที่ย้อนได้ให้มี "เลิกทำ" (undo)
- [ ] การกระทำทำลาย/ย้อนไม่ได้ ใช้ dialog ยืนยัน ระบุผลลัพธ์ตรง ๆ ("ลบรายงาน 3 ฉบับ") ปุ่มยืนยันใช้คำกริยาเดียวกัน ไม่ใช่ "ตกลง"

## 6. Motion / Micro-interaction

### 6.1 หลัก (Atlassian R14 **[ยืนยัน]**, MDN R15, WCAG 2.3.3 R16)
- ลูกเล่นต้อง "มีหน้าที่": ยืนยันการกระทำ, แสดงความคืบหน้า, นำสายตา, เชื่อมสถานะก่อน-หลัง — ไม่ใช่ตกแต่งอย่างเดียว; โฟกัสทีละจุด
- ความถี่สูง (hover/กด) ≤ 150 ms; transition ปานกลาง (เปิด dropdown/modal/แผง) 150–400 ms (ตัวอย่าง dropdown 150 ms, modal 250 ms); การเปลี่ยนใหญ่ครั้งเดียวต่อ session (ฉลอง) ขยายได้ถึง ~600–800 ms **[อนุมาน ส่วนเพดาน]**; ทางออก (ปิด) เร็วกว่าทางเข้า
- Easing ที่ใช้ได้ (Atlassian **[ยืนยัน]**): เข้า `cubic-bezier(0, 0.4, 0, 1)` · ย้าย/ขยาย `cubic-bezier(0.4, 0, 0, 1)` · ออก `cubic-bezier(0.6, 0, 0.8, 0.6)` · hover/popup เบา `cubic-bezier(0.4, 1, 0.6, 1)`. *Material 3 token ค่าตัวเลข: เปิดหน้า m3.material.io ไม่ได้ (โหลดด้วย JS) จึงไม่อ้างค่า*
- **ห้าม overshoot/bounce** ที่ใช้ใน toast ปัจจุบัน (`globals.css:185`) กับงานปกติ; ห้ามกระพริบ/สั่น/กวาดทั้งจอ (Atlassian); ห้ามกระพริบเกิน 3 ครั้ง/วินาที (WCAG 2.3.1 **[อนุมาน ความรู้ทั่วไป ไม่ได้เปิดหน้า]**); เนื้อหาเคลื่อนไหวอัตโนมัติ >5 วินาที ต้องหยุดได้ (WCAG 2.2.2, R6 **[ยืนยัน]**)
- เคลื่อนไหวเฉพาะ `transform` และ `opacity` (ลื่นบนเครื่องเก่า); ห้าม animate `width/height/top/left` เป็นหลัก

### 6.2 ที่ช่วย vs ที่รบกวน
| ช่วยเข้าใจ (ใช้) | รบกวน (ห้าม/จำกัด) |
|---|---|
| ปุ่ม pressed/hover เปลี่ยนสี-ยกเล็กน้อย 100–150 ms | ลอยวนไม่จบ (`.ll-spark`) บนหน้าที่ต้องอ่าน |
| Progress bar/ring เลื่อนเปลี่ยนค่าช้า ๆ 400–600 ms | ตัวเลขนับวิ่งนานเกิน 1 s |
| Toast/Card เลื่อนเข้า 200–250 ms + fade | Parallax, auto-carousel, scroll-jacking |
| Accordion/แผงขยายแบบ height-fade 200–250 ms | Bounce/elastic/shake ใส่ฟอร์ม (ผู้ใช้เข้าใจเป็นความผิดพลาด) |
| Skeleton shimmer เบา ๆ (ปิดได้) | Confetti เต็มจอทุกการกด/ซ้ำบ่อย |
| จุดเน้นแบบ highlight สีอ่อนให้แถวที่เพิ่งเพิ่ม 1.2–2 s แล้วจาง | เสียงอัตโนมัติ (WCAG G171: เฉพาะเมื่อผู้ใช้ขอ) |

### 6.3 `prefers-reduced-motion` (MDN **[ยืนยัน]** — Baseline widely available ตั้งแต่ ม.ค. 2020, R15; WCAG 2.3.3 C39 เป็นเทคนิคที่ยอมรับ R16)
กฎ: ออกแบบให้ "ใช้งานครบแม้ปิด motion ทั้งหมด" (Atlassian: reduced = "off and instant")
```css
:root { --dur-fast:120ms; --dur-base:220ms; --dur-slow:400ms;
        --ease-out:cubic-bezier(0,.4,0,1); --ease-move:cubic-bezier(.4,0,0,1); }
@media (prefers-reduced-motion: reduce) {
  *,*::before,*::after { animation-duration:.01ms !important; animation-iteration-count:1 !important;
                         transition-duration:.01ms !important; scroll-behavior:auto !important; }
  .skeleton { animation:none; }      /* คงสีพื้นนิ่ง */
  .confetti, .ll-spark { display:none; }  /* ฉลองด้วยข้อความ+ไอคอนแทน */
}
```
(รูปแบบ reset นี้เป็นแพตเทิร์นทั่วไป **[อนุมาน]**; MDN ยืนยัน syntax/ค่า `reduce`)
นอกจากนี้: ข้อมูลที่สื่อด้วย motion ต้องมีทางสื่อแบบนิ่งด้วย (เช่น progress ring ยังแสดงตัวเลข %); ทดสอบโดยเปิด "Reduce motion" ของ OS/Chrome DevTools rendering emulation

## 9. Checklist ย่อสำหรับ ui-inspector / reviewer (ติ๊กต่อหน้า)
1. ตัวอักษรเนื้อหา ≥16px, ไม่มีข้อความอ่านที่ <14px, line-height ไทย ≥1.6, ไม่มี uppercase/letter-spacing กว้างกับไทย
2. ทุกคู่สี text ≥4.5:1 / UI ≥3:1 (ตรวจจากตารางของ palette ที่เลือก ไม่ใช่ตาเปล่า)
3. ปุ่ม/ช่องกรอกสูง ≥44px (≥24px เด็ดขาด); ระยะห่างระหว่างเป้า ≥8px
4. Focus ring เห็นชัดทุก element ที่โต้ตอบได้; ใช้คีย์บอร์ดครบ
5. สถานะทุกอย่างมี สี+ไอคอน+ข้อความ; จำลองสีบอดแล้วยังแยกออก
6. มีครบ 4 state ทุกรายการข้อมูล: loading, empty (มีปุ่มทำต่อ), error (บอกวิธีแก้), success
7. ลูกเล่นทุกจุดมี "หน้าที่" ระบุได้; ไม่มี bounce/วนไม่จบ; reduced-motion ปิดครบ
8. หน้า login/loading/logout/landing/app ใช้ token ชุดเดียวกัน
9. ขยายเบราว์เซอร์ 200% และ text-spacing 1.4.12 แล้วไม่พัง
10. ไม่มี gamification ข้อห้ามข้อ 7

## 11. ช่องว่าง / ข้อเสนอต่อ architect
1. **ตัดสินใจฟอนต์:** แนะนำ Sarabun เป็น body (หลักฐานทิศทาง R1 + อยู่ใน repo + ต่อเนื่องกับ DOCX) แต่ขอ ui-inspector render เปรียบเทียบ Sarabun vs IBM Plex Sans Thai บนหน้าจริง (ไทยมีวรรณยุกต์ซ้อน, ตัวเลข KPI) ก่อนล็อก
2. **เลือก palette:** A หรือ B (C ติดปัญหาสถานะซ้อนสีหลัก). ใส่ค่าเป็น CSS variables ในที่เดียว และเก็บชื่อโทเคนเดิมที่ใช้อยู่ให้ migrate ง่าย (ระวังชื่อ `--brown-*` ที่ใช้ทั่ว `globals.css`)
3. กำหนด token ไว้ใน ADR: ขนาดตัวอักษร (14/16/18/22/28/36), line-height, radius (8–12px, ไม่ pill 50px กับปุ่มหลักก็ได้แต่ต้องคงเป้า ≥44px), spacing (4px grid), duration/easing ตามข้อ 6, ระดับ shadow 3 ระดับ
4. ข้อเสนอลูกเล่น (CSS ล้วน): progress ring SVG, เส้นเช็กถูกวาด (stroke-dashoffset), skeleton shimmer, card ยกเบา ๆ ตอน hover, แถวใหม่ highlight จาง, คำทักทาย/สรุป "วันนี้ต้องทำ" — ทั้งหมดไม่ต้องมี lib. **ไม่แนะนำเพิ่ม lib** (framer-motion/lottie/confetti) เพราะทุกอย่างทำด้วย CSS+SVG ได้ และเพิ่มขนาด bundle/ความเสี่ยงต่อ reduced-motion
5. ตัวควบคุมขนาดตัวอักษรให้ผู้ใช้ (ข้อ 1.1) — ถ้าอยู่นอก scope ให้เป็น backlog ที่ ADR บันทึกไว้
6. ควรให้ E2E เพิ่มเช็กอัตโนมัติ: ไม่มีข้อความ <14px, ขนาดเป้า ≥24px (ตรวจ computed style ด้วย Playwright ที่มีอยู่แล้ว) และ `emulateMedia({ reducedMotion: 'reduce' })` ผ่าน
